1. Qué es AI OS Core y para qué sirve

AI OS Core es el plano de control de la plataforma AI OS: un servicio REST local (FastAPI + SQLite) que no ejecuta modelos ni agentes, sino que decide, registra y vigila lo que hacen los demás componentes del ecosistema del TFM: AI Broker, Model Drift, Athena, Agora, Gestión Tareas IA, Knowledge Orchestrator y ChatyGPT.

Su papel se resume en cinco verbos:

  • Orientar: es la autoridad canónica de las metas (Goals) y sus objetivos.
  • Conocer: mantiene el catálogo de servicios federados, sus capacidades, un grafo ligero de recursos y la correspondencia entre identidades globales y los ids nativos de cada sistema.
  • Autorizar: evalúa políticas con lógica de tres valores, gestiona aprobaciones humanas de uso limitado y reservas de presupuesto, y combina techos de autonomía antes de dejar que un plan se despache.
  • Recordar: recibe eventos de los demás servicios con garantías de orden y deduplicación, guarda la última foto válida de cada recurso, aparta a cuarentena lo contradictorio y conserva paquetes de contexto inmutables.
  • Recuperar: tras un corte, dice si una operación debe reenviarse, seguirse o reconciliarse a mano, para no duplicar efectos.
Idea claveCore es determinista: con las mismas entradas da siempre la misma decisión, y deja traza de cada una. Los servicios que hacen el trabajo (Broker, Agora…) le consultan antes de actuar y le informan después.

2. Arquitectura en una página

API (FastAPI)api/routes/*: un router por dominio, validación Pydantic, formato de error único y middleware de idempotencia.
Aplicaciónapplication/*_service.py: casos de uso (crear meta, evaluar políticas, decidir plan…).
Dominiodomain/*: entidades puras e invariantes (precedencia de decisiones, lógica ternaria, niveles A0–A5).
Repositoriosinfrastructure/db/repositories: SQL explícito, transacciones BEGIN IMMEDIATE.
SQLite WALUn único fichero, synchronous=FULL, migraciones sólo hacia delante, aplicadas al arrancar.
Seguridad de redinfrastructure/http/security_client.py: validación SSRF y allowlist de hosts.

Core no hace llamadas salientes: el registro de un servicio valida su URL pero no la visita. Los demás servicios hablan con Core y no al revés. Esto lo mantiene arrancable “con cero dependencias”, como exige la especificación (P01).

4. Convenciones de la API

  • Prefijo común /api/v1 salvo /health y /ready. Cuerpos y respuestas en JSON UTF-8.
  • Las fechas son ISO 8601. Core las guarda en UTC; acepta Z o desfases (+02:00) y rechaza textos que no sean fechas.
  • Si no das un identificador, Core lo genera con prefijo: goal_…, obj_…, resv_…, ctx_…, plan_….
  • Los listados paginados aceptan limit (1–100, por defecto 50) y offset, y devuelven {items, total_returned, limit, offset} con orden estable.

Códigos de estado

CódigoSignificado en Core
200 / 201Lectura correcta / recurso creado
400Valor inválido: estado, fecha, operador, nivel, URL bloqueada por SSRF, referencia a un padre inexistente
403Denegado: aprobación caducada, revocada, agotada o de otro digest; principal sin scope o sin clearance suficiente
404No existe lo que pides
409Choca con lo ya registrado: id repetido, revisión obsoleta, saldo insuficiente, reserva ya consumida, clave de idempotencia reutilizada o en curso
422Falta un campo obligatorio o tiene el tipo equivocado (validación del esquema)

Formato de error

{
  "error":  { "type": "Conflict", "message": "Goal 'g1' ya existe.", "details": {} },
  "detail": "…"        // sólo en errores HTTP genéricos, por compatibilidad
}

Los ejemplos de este manual usan curl. En PowerShell, sustituye por Invoke-RestMethod -Method Post -Uri … -ContentType 'application/json' -Body '…', o usa Swagger UI.

5. Flujo: comprobar que el servicio está vivo

GET /health responde siempre que el proceso viva; GET /ready además abre la base y devuelve la versión de esquema (503 si no puede).

curl http://127.0.0.1:8000/health
{"status":"healthy","service":"ai_os_core","version":"0.2.0"}

curl http://127.0.0.1:8000/ready
{"status":"ready","service":"ai_os_core","schema_version":2}

6. Flujo: metas, objetivos y auditoría

Una meta (Goal) es el “para qué” de alto nivel; los objetivos la descomponen. Toda tarea o plan del ecosistema debería poder colgarse de una meta. Cada cambio de estado incrementa la revision y queda auditado.

Estados válidos: pending, active (inicial), paused, completed, failed, cancelled.

  1. Crear la meta POST /api/v1/goals 
    curl -X POST http://127.0.0.1:8000/api/v1/goals -H "Content-Type: application/json" -d "{\"goal_id\":\"goal_tfm\",\"title\":\"Entregar el TFM\",\"description\":\"Memoria y defensa\",\"owner_service\":\"gestion_tareas\"}"
    Campos: title y description obligatorios; goal_id, owner_service (por defecto ai_os_core) y parent_goal_id opcionales. Repetir un goal_id existente da 409 (nunca sobrescribe); un padre inexistente da 400.
  2. Añadir objetivos POST /api/v1/objectives con {"goal_id":"goal_tfm","title":"Redactar capítulo 3"}.
  3. Consultar: GET /api/v1/goals/{id}, GET /api/v1/goals?limit=50&offset=0, GET /api/v1/goals/{id}/objectives, GET /api/v1/objectives/{id}.
  4. Cambiar estado PATCH /api/v1/goals/{id}/status o /api/v1/objectives/{id}/status con {"status":"completed","principal_id":"usuario"}. La revisión sube en uno.
  5. Ver la traza GET /api/v1/goals/{id}/audit: lista append-only de creación y cambios, con quién y cuándo.

7. Flujo: registro de servicios y capacidades

Core mantiene el catálogo de servicios del ecosistema y de lo que cada uno sabe hacer. Al registrar, valida la URL contra ataques SSRF; no la visita.

  1. Registrar (o actualizar) un servicio POST /api/v1/services 
    { "service_id": "ai_broker", "name": "AI Broker", "base_url": "http://192.168.1.52:8765",
  "version": "2.11", "health_status": "healthy", "capabilities": ["llm.task"],
  "metadata": { "auth_header": "X-Admin-Token" } }
    Repetir el mismo service_id actualiza el registro (es idempotente). health_status: healthy, degraded, down, unknown.
  2. Declarar capacidades POST /api/v1/capabilities con capability_id, name, description, provider_service_id y opcionalmente input_schema/output_schema. El proveedor debe estar registrado (si no, 400).
  3. Consultar: GET /api/v1/services, /api/v1/services/{id}, /api/v1/capabilities/{id}.

8. Flujo: políticas y decisión de autorización

Una política dice: “en este scope, si se cumplen estas condiciones, la decisión es X”. Core evalúa todas las políticas habilitadas del scope (y las de scope *) contra un contexto y devuelve una decisión consolidada.

Lógica de tres valores

Cada condición da TRUE, FALSE o UNKNOWN. Un dato ausente, nulo o no comparable (un texto contra greater_than) es UNKNOWN: Core nunca adivina.

OperadorUsoAusente / null
existsEl campo está en el contexto (aunque sea null)FALSE si ausente
equals, not_equalsIgualdad. equals con value: null pregunta “¿es null?”UNKNOWN
greater_than, less_than, greater_or_equal, less_or_equalComparación numérica u ordenableUNKNOWN
inPertenencia; value debe ser una listaUNKNOWN

condition_mode: all (algún FALSE → FALSE; si no, algún UNKNOWN → UNKNOWN) o any (algún TRUE → TRUE; si no, algún UNKNOWN → UNKNOWN). Una política sin condiciones sólo es válida con unconditional: true. Operadores o modos desconocidos se rechazan al crear (400).

Combinación

  • Precedencia estricta: DENY > REQUIRE_APPROVAL > INDETERMINATE > ALLOW.
  • Sin ninguna política en el scope → DENY (denegar por defecto).
  • Una política restrictiva que no se puede evaluar aporta INDETERMINATE: un “DENY si coste > 5” sin coste no queda tapado por un ALLOW.
  • Restricciones max_* se quedan con la más baja y min_* con la más alta; si un mínimo supera a su máximo → DENY. Las obligations se acumulan.
  • executable sólo es true con ALLOW y sin incógnitas de seguridad (campos cuyo nombre contiene security o auth); una aprobación humana no resuelve esas incógnitas.
  1. Crear políticas POST /api/v1/policies 
    { "policy_id": "pol_conf", "policy_key": "confidencial_requiere_aprobacion", "scope": "broker:invoke",
  "decision_if_matched": "REQUIRE_APPROVAL",
  "conditions": [ { "field": "data_classification", "operator": "in", "value": ["confidential","local_only"] } ] }

{ "policy_id": "pol_cost", "policy_key": "coste_maximo", "scope": "broker:invoke",
  "decision_if_matched": "DENY",
  "conditions": [ { "field": "estimated_cost", "operator": "greater_than", "value": 5 } ] }

{ "policy_id": "pol_base", "policy_key": "auditar_siempre", "scope": "broker:invoke",
  "decision_if_matched": "ALLOW", "unconditional": true,
  "obligations": ["audit_trace"], "constraints": { "max_output_tokens": 600 } }
    Reenviar el mismo policy_id la actualiza. enabled: false la desactiva sin borrarla.
  2. Evaluar POST /api/v1/policies/evaluate 
    { "scope": "broker:invoke", "principal_id": "chatygpt",
  "context": { "data_classification": "internal", "estimated_cost": 0.5 } }
→ { "authorization": "ALLOW", "constraints": {"max_output_tokens": 600},
    "obligations": ["audit_trace"], "matched_policy_refs": ["pol_base"],
    "unknown_inputs": [], "executable": true }
    Con confidential el resultado es REQUIRE_APPROVAL; sin estimated_cost, INDETERMINATE con unknown_inputs: ["estimated_cost"]. Cada evaluación deja una traza de decisión con el hash del contexto.
  3. Revisar GET /api/v1/policies o /api/v1/policies?scope=broker:invoke.

9. Flujo: aprobaciones humanas

Una autorización es un permiso concedido (normalmente por una persona) con un número máximo de usos, caducidad opcional y, si se quiere, ligado a una acción exacta mediante su digest. Es inmutable: no se edita, se revoca.

  1. Conceder POST /api/v1/approvals 
    { "authorization_id": "auth_publicar_42", "scope": "broker:invoke", "max_uses": 1,
  "expires_at": "2026-10-08T18:00:00+01:00", "expected_digest": "9f3c…", "granted_by": "usuario" }
    max_uses ≥ 1. Con expected_digest la autorización es exact_action: sólo vale para la operación cuyo hash coincide. Sin él es scoped: vale para cualquier operación del scope.
  2. Consumir un uso justo antes de actuar POST /api/v1/approvals/use 
    { "use_id": "use_1", "authorization_id": "auth_publicar_42",
  "operation_id": "op_publicar_42", "operation_digest": "9f3c…" }
→ {"status":"committed","use_id":"use_1"}
    Reglas: caducada, revocada, agotada o digest distinto del aprobado → 403. Repetir el mismo operation_id con el mismo digest es un reintento legítimo y no gasta otro uso; con distinto digest → 409. Si dos operaciones compiten por el último uso, sólo una lo consigue (verificado con 10 peticiones simultáneas).
  3. Ver el estado GET /api/v1/approvals/{id}/status → status (active, consumed, expired, revoked), used_count, remaining_uses.
  4. Revocar POST /api/v1/approvals/{id}/revoke con {"revoked_by":"usuario","reason":"…"}. Revocar dos veces no cambia nada.

10. Flujo: presupuesto y reservas

Antes de una operación con coste se reserva saldo; al terminar se consume (o se libera si no se hizo). Así dos operaciones simultáneas no pueden gastar el mismo dinero.

  1. Abrir cuenta POST /api/v1/budget/accounts con {"account_id":"broker_cloud","balance":20} (409 si ya existe).
  2. Reservar POST /api/v1/budget/reserve con {"account_id":"broker_cloud","amount":0.5,"reservation_id":"resv_1","expires_at":"…"}. Saldo disponible insuficiente → 409; cuenta inexistente → 404; reservation_id repetido → 409.
  3. Consumir POST /api/v1/budget/consume con {"reservation_id":"resv_1"}: descuenta del saldo. Consumir dos veces → 409.
  4. o Liberar POST /api/v1/budget/release: devuelve el importe al disponible. Liberar una consumida → 409; una inexistente → 404; dos veces → sin efecto.
  5. Consultar: GET /api/v1/budget/accounts/{id} → balance, reserved, available; GET /api/v1/budget/reservations/{id} → estado reserved, consumed, released o expired.
CaducidadUna reserva con expires_at vencido y sin consumir se marca expired y su importe vuelve al disponible la próxima vez que se reserva o consume en esa cuenta.

11. Flujo: bandeja de eventos y proyección canónica

Los servicios informan a Core de los cambios mediante eventos. Cada productor numera sus eventos por flujo (producer_id + stream_id + stream_epoch) con source_sequence consecutiva. Core guarda todos los eventos y mantiene la proyección canónica de cada recurso: el último full_state válido de mayor revisión.

event_typeEfecto
full_stateFoto completa del recurso. Es el único tipo que cambia la proyección canónica.
delta, audit, notificationSe guardan y cuentan para la secuencia, pero no cambian la proyección.
  1. Enviar POST /api/v1/events/inbox 
    { "event_id": "ev_001", "producer_id": "ai_broker", "stream_id": "tasks", "stream_epoch": 1,
  "source_sequence": 1, "event_type": "full_state", "resource_id": "broker_task:abc",
  "resource_type": "broker_task", "revision": 2, "payload": {"status": "completed"},
  "state_digest": "sha256-del-estado" }
→ { "event_id": "ev_001", "accepted_in_canonical_projection": true,
    "quarantine": false, "duplicate": false, "reason": null }
  2. Leer la versión vigente GET /api/v1/events/canonical/{resource_id} → revisión, payload, digest y fecha.
  3. Revisar incidencias: GET /api/v1/events/gaps (saltos de secuencia sin resolver) y GET /api/v1/events/quarantine (eventos apartados).

Qué pasa en cada caso

CasoRespuesta de Core
Reentrega del mismo event_id (reintento de red)200 con duplicate: true; no se reprocesa.
Otro evento con una secuencia ya ocupada409.
Salto de secuencia (llega la 5 tras la 1)Se registra un REPLAY_GAP y el evento va a cuarentena (C05).
Dos full_state de la misma revisión con distinto state_digestEl segundo va a cuarentena (C03).
full_state tardío de revisión menorSe guarda para auditoría pero la proyección no retrocede (C02).

12. Flujo: restore y recibos de operación

Tras una caída, la pregunta es “¿reenvío o no?”. Los receptores registran recibos del estado de cada operación y Core traduce ese estado en una acción recomendada.

  1. El receptor informa POST /api/v1/operations/receipts con {"operation_id":"op_42","receiver_service":"ai_broker","status":"in_progress","evidence":{"task_id":"task_…"}}. Se puede reenviar con el estado nuevo.
  2. Quien va a reenviar consulta POST /api/v1/operations/status con {"operation_id":"op_42","target_service_id":"ai_broker"}.
Estado del reciborecommended_actionQué hacer
sin recibo (not_seen)retry_allowedReenviar con el mismo operation_id, tras revalidar política y aprobación
accepted, in_progressfollow_up_no_resendNo reenviar; seguir consultando
succeededreconstruct_state_no_resendReconstruir el estado local a partir del resultado
failed_terminal, cancelleddo_not_resend_without_new_decisionSólo con una decisión/operación nueva
unknownmanual_reconciliation_requiredRevisión humana

13. Flujo: grafo de recursos e identidades

El grafo de recursos es un mapa ligero de qué existe en el ecosistema y cómo se relaciona (una tarea “ejecutada por” un trabajo de Agora, un objetivo “cumplido por” una tarea del Broker). Los identity bindings traducen un id global de AI OS al id nativo de cada sistema.

  1. Proyectar un recurso PUT /api/v1/resources con {"resource_id":"task_77","resource_type":"task","owner_service":"gestion_tareas","revision":3,"data":{…}}. El propietario no puede cambiar y la revisión no puede bajar (409 en ambos casos).
  2. Relacionar POST /api/v1/resources/relations con {"source_id":"obj_1","target_id":"task_77","relation_type":"fulfilled_by"}. Ambos deben existir; repetir no duplica.
  3. Consultar GET /api/v1/resources/{id}: el recurso y sus relaciones salientes.
  4. Vincular identidades PUT /api/v1/identity-bindings con {"global_id":"op_42","native_id":"task_9f2c","source_system":"ai_broker","adapter_revision":1}; resolver con GET /api/v1/identity-bindings/{global_id}/{source_system}. Una adapter_revision menor que la registrada → 409.

14. Flujo: proyección de certificaciones

Model Drift evalúa si un modelo está certificado para una capacidad. Core guarda una proyección de ese veredicto para poder consultarlo al decidir, sin llamar a Model Drift.

  1. Registrar POST /api/v1/certifications 
    { "model_id": "gemma4:12b", "capability_id": "llm.task", "version": "1",
  "source_system": "model_drift", "evaluation_verdict": "CERTIFIED",
  "is_applicable": true, "revision": 5 }
    Veredictos: CERTIFIED, REJECTED, INDETERMINATE, EXPIRED. Una revisión igual o mayor actualiza; una menor (llegada tarde) → 409 y la proyección no cambia.
  2. Consultar GET /api/v1/certifications o /api/v1/certifications/{model_id}/{capability_id}/{version}.

15. Flujo: paquetes de contexto

Un ContextPackage fija, de forma inmutable, el contexto exacto con que se tomó una decisión o se lanzó una tarea, para poder reproducirlo después aunque las fuentes cambien. Su snapshot_hash es un SHA-256 determinista del contenido.

  1. Crear POST /api/v1/context/packages 
    { "goal_id": "goal_tfm", "classification_level": "INTERNAL",
  "resources": [ { "resource_id": "obj_1", "resource_type": "objective", "owner_service": "ai_os_core" } ],
  "payload": { "prompt_digest": "9f3c…" },
  "principal_id": "athena", "principal_role": "agent",
  "principal_clearance": "INTERNAL", "principal_scopes": ["context:build"] }
    Niveles: PUBLIC < INTERNAL < CONFIDENTIAL < RESTRICTED. Sin el scope context:build, o pidiendo un nivel por encima del clearance del principal → 403. Niveles ilegibles → 400.
  2. Recuperar por id GET /api/v1/context/packages/{id} o por hash GET /api/v1/context/snapshots/{hash}.

16. Flujo: planificador tipado y autonomía

Un planificador (persona o agente) propone un plan tipado: una lista de tareas asignadas a servicios, colgado de una meta, con un nivel de autonomía solicitado y la decisión de política que lo respalda. Core lo guarda y, cuando se pide, decide si puede despacharse combinando los techos de autonomía aplicables.

NivelSignificado
A0Totalmente supervisado: nunca se despacha solo
A1Asistido, confirmación en cada paso
A2Semiautónomo con aprobación de inicio
A3Autónomo condicionado a políticas y presupuesto
A4Alta autonomía con auditoría posterior
A5Totalmente autónomo dentro del sandbox
  1. Proponer POST /api/v1/planner/proposals 
    { "goal_id": "goal_tfm", "requested_autonomy": "A3",
  "policy_decision": { "authorization": "ALLOW", "executable": true },
  "tasks": [
    { "task_id": "resumir", "title": "Resumir fuentes", "description": "Tarea LLM",
      "assigned_service": "ai_broker", "requires_human_approval": false, "estimated_duration_sec": 120 },
    { "task_id": "publicar", "title": "Publicar", "description": "Acción irreversible",
      "assigned_service": "agora", "requires_human_approval": true } ],
  "principal_id": "athena", "principal_scopes": ["planner:propose"] }
    La meta debe existir (404), hace falta al menos una tarea con task_id únicos (400) y el principal necesita el scope planner:propose (403).
  2. Decidir POST /api/v1/planner/proposals/{id}/decision con {"applicable_ceilings":["A3","A4"]}. 
    → { "approved_for_dispatch": true, "effective_autonomy": "A3",
    "reasons": ["Aprobado para despacho con nivel efectivo A3."] }

Reglas de la decisión

  • La autonomía efectiva es el mínimo entre la solicitada y todos los techos. Ninguna capa la eleva.
  • Un techo ilegible (p. ej. "A1x") → 400: ignorarlo subiría la autonomía.
  • No se despacha si la política adjunta no es ALLOW, si no es ejecutable, si el nivel efectivo es A0, o si alguna tarea requiere aprobación humana y el nivel es A0–A1. Todas las razones aparecen en reasons.
ImportanteCore decide si un plan puede despacharse; no lo despacha. Crear las tareas en Gestión Tareas IA o las tarjetas en Agora es responsabilidad de quien pidió la decisión.

17. Idempotencia de peticiones

Cualquier petición POST/PUT/PATCH puede hacerse segura frente a reintentos añadiendo la cabecera X-Idempotency-Key (o Idempotency-Key). Opcionalmente: X-Principal-Id (quién llama) y X-Operation-Id.

  • La clave vale dentro de su espacio principal + método y ruta + clave. La misma clave usada por otro principal o en otra ruta es otra operación.
  • Misma clave y mismo cuerpo → se devuelve la respuesta original con X-Idempotent-Replay: true; no se repite el efecto.
  • Misma clave y cuerpo distinto → 409 IdempotencyConflict.
  • Misma clave mientras la primera petición aún se procesa → 409 IdempotencyInProgress con Retry-After: 1.
  • Si la operación falla con error 5xx, la clave se libera y puede reintentarse. Las respuestas 4xx sí quedan registradas.
curl -X POST http://127.0.0.1:8000/api/v1/goals -H "Content-Type: application/json" ^
     -H "X-Idempotency-Key: alta-meta-tfm" -H "X-Principal-Id: gestion_tareas" ^
     -d "{\"title\":\"Entregar el TFM\",\"description\":\"…\"}"

18. Recorrido completo con el Broker y Agora

Este es el flujo que se ejecutó de verdad el 7 de octubre de 2026 contra el AI Broker del PC IA (http://192.168.1.52:8765, contrato 2.11) y el tablero de Agora de este equipo (https://127.0.0.1:8741). Superó 29 comprobaciones. Sirve como plantilla para integrar cualquier cliente.

  1. Comprobar Core: /health y /ready.
  2. Registrar los servicios reales: ai_broker (IP privada de la LAN, admitida) y agora_board (loopback https), y la capacidad llm.task. Se comprueba que una capacidad de un proveedor inexistente se rechaza.
  3. Crear meta y objetivo para la tarea.
  4. Definir y evaluar políticas del scope broker:invoke: datos internos y baratos → ALLOW ejecutable con obligación audit_trace y tope de 600 tokens; datos confidenciales → REQUIRE_APPROVAL; sin coste → INDETERMINATE.
  5. Reservar presupuesto (0,5 sobre una cuenta de 2).
  6. Calcular el digest del cuerpo exacto que se enviará al Broker, conceder una aprobación exact_action de un uso con ese digest y consumirla. Un digest manipulado se rechaza con 403.
  7. Fijar el contexto en un ContextPackage y registrar el plan (Broker + Agora); la decisión sale aprobada en A3.
  8. Restore previo: la operación aún no existe → retry_allowed; se registra el recibo accepted.
  9. Invocar al Broker (POST /api/v1/tasks con cabecera X-Admin-Token, clave de idempotencia estable y risk.data_classification tomado del contexto evaluado). Recibo in_progress con el task_id → follow_up_no_resend. Sondeo hasta completed.
  10. Cerrar: recibo succeeded con el hash del resultado → reconstruct_state_no_resend; eventos full_state de la tarea (un evento tardío no hace retroceder la proyección); consumo del presupuesto; relación objetivo → tarea en el grafo; identity binding operación → task_id; objetivo a completed.
  11. Idempotencia del Broker: reenviar la misma petición devuelve la misma tarea, no una nueva.
  12. Agora (sólo lectura): se lee el tablero y los perfiles con el token Bearer del tablero y se proyecta una foto en Core como full_state de agora:board.

Respuesta real obtenida del Broker: “Un plano de control sirve para coordinar y gestionar los recursos y operaciones del sistema distribuido, asegurando su correcto funcionamiento y comunicación entre sus componentes.”

Cómo repetirloEl guion es python scriptse2e_broker_agora.py <url_core> <token_broker> <token_agora>. Necesita el PC IA encendido, el tablero de Agora arrancado (C:\Agora\Agora Tablero.cmd) y el certificado C:\Agora\pki\ca.crt. El Broker cambia su token en cada arranque: si da 403, pide el token nuevo. En Agora no se crean tarjetas, porque eso encargaría trabajo real al PC IA.

22. Límites conocidos

Sin autenticaciónCore no comprueba quién llama: X-Principal-Id, los scopes y el clearance los declara el propio cliente en la petición. Está pensado para escuchar sólo en 127.0.0.1. No lo expongas en la red sin poner delante un proxy con autenticación.
  • Un REPLAY_GAP se registra y se pone en cuarentena, pero no hay todavía endpoint para marcarlo resuelto ni flujo automático de snapshot y nueva línea base (§6.4 de la especificación).
  • Las políticas no se borran: se desactivan con enabled: false. Metas, objetivos y recursos tampoco tienen borrado.
  • La “incógnita de seguridad” (C20) se detecta por el nombre del campo (security, auth).
  • No hay outbox de comandos activo: la tabla command_outbox existe pero ningún flujo la usa todavía; tampoco hay endpoint para consultar las trazas de decisión de políticas (se guardan en decision_traces).
  • La promoción y degradación de autonomía de P15 dependen de una AutonomyPolicyDefinition aceptada que aún no existe; hoy sólo se combinan techos.
